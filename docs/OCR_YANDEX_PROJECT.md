# OCR корейских изображений с Яндекс Диска

Техническая документация проекта. Детальная инструкция без серверных команд для
ребёнка находится в [`OCR_INSTRUCTION_FOR_CHILD.md`](./OCR_INSTRUCTION_FOR_CHILD.md).

## 1. Назначение и текущий статус

Проект преобразует изображения с корейским текстом из публичной папки Яндекс
Диска в отдельные UTF-8 TXT-файлы.

Текущая production-конфигурация на 13 июля 2026 года:

- источник: публичная папка `протокол` —
  <https://disk.yandex.ru/d/UeiGaC7MhEXjCw>;
- OCR: локальный PaddleOCR PP-OCRv5, mobile detector + Korean recognizer;
- результат: `/OCR/protocol/txt/<basename>.txt` на авторизованном Яндекс Диске;
- состояние заданий: `postgres.public.ocr_jobs`;
- оркестрация: активный workflow n8n
  `OCR — Yandex Disk Korean screenshots`, ID `KoreanOcrYd2026A`;
- OCR API слушает только `127.0.0.1:8765`;
- обработка последовательная, по одному изображению;
- production-проверка: 20 из 20 изображений обработаны, повторный запуск не
  вызвал повторный OCR неизменённых файлов.

Публичная папка-источник не принадлежит аккаунту, чей OAuth-токен использует
система. Поэтому Яндекс API не позволяет писать результат обратно в неё. TXT
сохраняются в принадлежащую авторизованному аккаунту папку
`/OCR/protocol/txt`.

## 2. Границы ответственности

Ребёнок:

1. готовит и нумерует изображения;
2. загружает их прямо в корень папки `протокол`;
3. сообщает взрослому диапазон номеров;
4. после завершения проверяет TXT по исходным картинкам.

Оператор:

1. проверяет готовность сервиса;
2. запускает batch;
3. контролирует статусы и ошибки;
4. при необходимости повторяет запуск или исправляет задание.

Автоматического запуска по факту загрузки сейчас нет. Batch стартует командой
`/ocr` в личном чате с ботом `@bibi_translation_review_bot`, локальным скриптом
или ручным запуском workflow в n8n. Команда доступна только владельцу бота.
После завершения бот присылает итог: сколько изображений найдено, распознано
заново, пропущено без изменений и завершилось ошибкой.

## 3. Архитектура и поток данных

```text
Публичная папка Яндекс Диска
        │ список файлов + временная ссылка на скачивание
        ▼
n8n workflow ───────► PostgreSQL ocr_jobs
        │                    │
        │ POST /ocr-url      │ статусы, попытки, метрики, ошибки
        ▼                    │
локальный FastAPI + PaddleOCR│
        │ распознанный текст │
        ▼                    │
n8n получает upload URL ◄────┘
        │
        ▼
/OCR/protocol/txt/<basename>.txt
```

Распределение ответственности:

- n8n перечисляет входные файлы, сортирует их, обеспечивает идемпотентность,
  получает временные URL, вызывает OCR и загружает TXT;
- FastAPI-сервис скачивает ровно одно изображение по короткоживущему URL,
  подготавливает его и возвращает распознанный текст с метриками;
- PostgreSQL хранит только служебное состояние. OCR-текст в БД не сохраняется;
- Яндекс Диск хранит исходные изображения и итоговые TXT;
- Infisical хранит OAuth-токен Яндекс Диска и токен batch-webhook.

## 5. Требования и ограничения входных файлов

Workflow принимает изображения, чей MIME type соответствует PNG, JPEG, WEBP
или TIFF. Файлы берутся только из корня публичной папки; подпапки не обходятся.

Рекомендации:

- одна страница на изображение;
- правильная ориентация;
- уникальные имена с естественной нумерацией: `1.png`, `2.png`, ...;
- не использовать одинаковый basename с разными расширениями: `1.png` и
  `1.jpg` оба пишут в `1.txt`;
- размер одного скачанного файла не более 20 MiB;
- текущий workflow запрашивает до 1000 файлов за batch без пагинации;
- новые файлы не следует добавлять или заменять во время активного batch.

Сортировка natural: `1.png`, `2.png`, `10.png`, а не лексикографическая
`1.png`, `10.png`, `2.png`.

## 6. Быстрый операторский сценарий

### 6.1 Проверить и запустить сервис

```bash
cd /home/user/n8n-docker
docker compose -f docker-compose.ocr.yml up -d --build
curl -fsS http://127.0.0.1:8765/health | jq
```

Успешный health-check содержит:

```json
{
  "status": "ok",
  "ready": true,
  "engine": "PaddleOCR",
  "engine_version": "PP-OCRv5",
  "language": "korean",
  "detection_model": "PP-OCRv5_mobile_det",
  "recognition_model": "korean_PP-OCRv5_mobile_rec"
}
```

Первый старт скачивает модели в именованный Docker volume `ocr_models` и может
занять заметно больше времени. Следующие рестарты используют кэш.

### 6.2 Запустить обработку

Основной пользовательский способ — открыть `@bibi_translation_review_bot` и
отправить:

```text
/ocr
```

Бот подтверждает приём команды, а после окончания присылает отчёт в тот же чат.
Повторная команда во время активного batch не запускает второй процесс.

Локальный операторский способ:

```bash
cd /home/user/n8n-docker
./scripts/run_ocr_batch.sh
```

Нормальный немедленный ответ:

```text
OCR batch accepted
```

Это означает, что n8n принял запрос, а не что все изображения уже готовы.

### 6.3 Проверить состояние

```bash
./scripts/ocr_status.sh
```

Ожидаемый финал без ошибок:

```text
status | count
-------+------
done   | ...
```

Нижняя таблица должна быть пустой. Она показывает только задания, чей статус не
`done`.

### 6.4 Проверить результат

Минимальная проверка:

1. число `done` равно числу поддерживаемых изображений в корне источника;
2. в `/OCR/protocol/txt` есть одноимённые непустые TXT;
3. первый, средний и последний файлы открываются как UTF-8;
4. в тексте нет символа замены `�`;
5. корейский текст визуально сравнен с исходником хотя бы выборочно.

## 7. Идемпотентность и повторные запуски

Уникальный ключ задания — `(source_public_key, source_path)`.

- неизменённый файл со статусом `done` пропускается;
- изменение MD5 переводит существующее задание в `pending`;
- `processing`, не обновлявшийся более 30 минут, переводится в `retry`;
- успешный новый результат загружается с `overwrite=true`;
- одна ошибка не останавливает остальные изображения;
- число попыток увеличивается перед каждым OCR;
- после четырёх попыток задание перестаёт автоматически обрабатываться.

Важное ограничение текущей версии: при изменении MD5 счётчик `attempts` не
сбрасывается. Обычная замена ранее успешного файла работает. Но файл, уже
исчерпавший четыре попытки, потребует операторского сброса счётчика:

```bash
docker exec n8n-docker-db-1 sh -lc \
  'psql -U "$POSTGRES_USER" -d postgres -v ON_ERROR_STOP=1 -c "
    UPDATE ocr_jobs
    SET status = '\''pending'\'', attempts = 0, error_message = NULL,
        updated_at = now()
    WHERE source_name = '\''7.png'\'';
  "'
```

Перед выполнением заменить `7.png` на точное имя проблемного файла и проверить
условие `WHERE` через `SELECT`.

## 8. Статусы задания

| Статус | Значение | Действие оператора |
|---|---|---|
| `pending` | новое или изменённое изображение | обычно ничего; запустить batch |
| `processing` | изображение сейчас обрабатывается | подождать; после 30 минут stale-job станет `retry` при следующем batch |
| `done` | TXT успешно загружен | выборочно проверить качество |
| `retry` | временная ошибка, попытки ещё есть | устранить причину и снова запустить batch |
| `failed` | обработка не удалась | посмотреть `error_message`; после 4 попыток нужен ручной reset |

Полная диагностическая выборка:

```bash
docker exec n8n-docker-db-1 sh -lc \
  'psql -U "$POSTGRES_USER" -d postgres -P pager=off -c "
    SELECT source_name, status, attempts, confidence, min_confidence,
           line_count, text_length, error_message, updated_at
    FROM ocr_jobs
    ORDER BY updated_at DESC;
  "'
```

Пакетные запуски и адресат Telegram-отчёта хранятся отдельно в
`ocr_batch_runs`. Одновременно допускается только одна запись со статусом
`running`; зависший более 12 часов batch автоматически закрывается как
`failed` при следующей команде.

## 9. API OCR-сервиса

### `GET /health`

Возвращает готовность и выбранные модели. Во время инициализации возможны
`status: starting` и `ready: false`.

### `POST /ocr-url`

Запрос:

```json
{
  "url": "https://temporary-download-url",
  "source_name": "1.png"
}
```

Ответ:

```json
{
  "text": "распознанный текст\n",
  "confidence": 0.91,
  "min_confidence": 0.62,
  "line_count": 27,
  "duration_ms": 19420,
  "engine": "PaddleOCR",
  "engine_version": "PP-OCRv5",
  "language": "korean",
  "preprocessed": true
}
```

Основные HTTP-ошибки:

| Код | Причина |
|---|---|
| 413 | изображение больше разрешённого лимита |
| 415 | URL вернул не изображение или файл повреждён |
| 422 | пустой файл или OCR не нашёл текст |
| 502 | исходное изображение не удалось скачать |
| 503 | OCR-модель ещё запускается |
| 500 | непредвиденная ошибка обработки |

## 10. Обработка изображения

Перед OCR сервис:

1. скачивает файл потоково с лимитом 20 MiB;
2. проверяет MIME type и возможность декодирования;
3. переводит изображение в оттенки серого;
4. инвертирует тёмный фон при средней яркости ниже 115;
5. применяет autocontrast;
6. увеличивает небольшие изображения максимум в два раза, пока длинная сторона
   не приблизится к 1800 px;
7. распознаёт текст;
8. сортирует боксы сверху вниз и слева направо, склеивает фрагменты строки и
   восстанавливает крупные вертикальные разрывы как абзацы;
9. удаляет временную директорию после запроса.

Строки с confidence ниже `OCR_MIN_SCORE` отбрасываются.

## 11. Конфигурация

Production-параметры задаются в `docker-compose.ocr.yml`:

| Переменная | Значение | Назначение |
|---|---:|---|
| `OCR_LANG` | `korean` | язык распознавания |
| `OCR_VERSION` | `PP-OCRv5` | семейство OCR |
| `OCR_DETECTION_MODEL` | `PP-OCRv5_mobile_det` | детектор текста |
| `OCR_RECOGNITION_MODEL` | `korean_PP-OCRv5_mobile_rec` | корейский recognizer |
| `OCR_MAX_CONCURRENCY` | `1` | защита inference object и bounded CPU/RAM |
| `OCR_MAX_IMAGE_BYTES` | `20971520` | максимум 20 MiB |
| `OCR_DOWNLOAD_TIMEOUT` | `45` | таймаут скачивания, секунды |
| `OCR_MIN_SCORE` | `0.35` | минимальная уверенность строки |
| `PADDLE_PDX_CACHE_HOME` | `/models` | постоянный кэш моделей |

Сервис использует один Uvicorn worker и работает от непривилегированного UID
10001.

## 12. Безопасность и данные

- OCR-порт привязан только к loopback `127.0.0.1` через host networking;
- batch-webhook защищён отдельным Header Auth token;
- `run_ocr_batch.sh` получает токен из Infisical и не печатает его;
- Yandex OAuth credential хранится n8n в зашифрованном виде;
- секреты не должны попадать в Markdown, shell history и логи;
- временные изображения находятся в tmpfs `/tmp/ocr` и удаляются после запроса;
- контейнер не логирует байты изображения и распознанный текст;
- PostgreSQL хранит метаданные и ошибку, но не OCR-текст;
- модельный кэш в `ocr_models` не содержит пользовательские изображения.

### Definition of Done для batch

1. health-check: `ready=true`;
2. workflow execution завершён без необработанного exception;
3. `ocr_status.sh`: все ожидаемые задания в `done`, нижняя таблица пуста;
4. количество непустых TXT совпадает с количеством входных изображений;
5. имена TXT совпадают с basename источников;
6. выборка TXT валидна как UTF-8 и не содержит replacement characters;
7. повторный запуск не увеличивает `attempts` у неизменённых `done`-заданий.

## 14. Производительность

На эталонных тёмных корейских скриншотах mobile detector обрабатывает страницу
примерно за 15–25 секунд на CPU. Batch из 20 страниц обычно занимает около
5–10 минут с учётом сетевых операций.

Оценка для 900 страниц при неизменной последовательной архитектуре — примерно
4–7 часов. Это плановая длительная обработка; перед таким запуском следует
проверить свободное место, устойчивость n8n и состояние очереди. Повышать
concurrency без отдельного нагрузочного теста нельзя: inference object не
считается thread-safe, а расход CPU/RAM существенно вырастет.

## 15. Диагностика

### Сервис не готов

```bash
docker compose -f docker-compose.ocr.yml ps
docker logs --tail 200 korean-ocr-service
curl -fsS http://127.0.0.1:8765/health | jq
```

На первом старте подождать загрузку моделей. Если контейнер перезапускается,
проверить сеть, память, место на диске и traceback в логах.

### Batch принят, но задания не движутся

1. проверить execution активного workflow `KoreanOcrYd2026A` в n8n;
2. запустить `./scripts/ocr_status.sh`;
3. проверить health OCR-сервиса;
4. проверить доступность source public link;
5. проверить, что в корне есть поддерживаемые изображения;
6. проверить Yandex credential, если ошибка возникла на upload URL.

### Отдельный файл в `retry` или `failed`

Посмотреть `error_message`, имя и число попыток. Типовая развилка:

- download error — проверить публичную ссылку и повторить batch;
- 413 — уменьшить изображение;
- 415 — пересохранить в PNG;
- 422 — улучшить качество/ориентацию или обработать вручную;
- upload error — проверить OAuth credential и квоту Яндекс Диска;
- четыре попытки — после исправления причины вручную сбросить задание.

### Результат есть, но качество низкое

Сравнить исходник, `confidence`, `min_confidence` и `line_count`. Проверить
ориентацию, размытие, размер шрифта и контраст. Не снижать `OCR_MIN_SCORE`
глобально без контрольной выборки: это добавит мусорные строки во все файлы.

## 16. Обслуживание и rollback

### Перезапуск без пересборки

```bash
cd /home/user/n8n-docker
docker compose -f docker-compose.ocr.yml restart ocr-service
```

### Пересборка после изменения кода

```bash
docker compose -f docker-compose.ocr.yml up -d --build ocr-service
curl -fsS http://127.0.0.1:8765/health | jq
```

### Остановка

```bash
docker compose -f docker-compose.ocr.yml stop ocr-service
```

Не использовать `down -v` без осознанной причины: ключ `-v` удалит кэш моделей
и следующий запуск снова будет их скачивать.

### Workflow rollback

- перед изменением экспортировать текущий workflow из n8n;
- сохранить экспорт в `/home/user/n8n-backups/`;
- для отката деактивировать неисправную версию, импортировать проверенный JSON,
  заново привязать credentials и провести smoke-test на одном изображении;
- не активировать две версии с одинаковым production webhook path.

Существующие исходные изображения и TXT не удалять при rollback. Таблица
`ocr_jobs` нужна для идемпотентности; её очистка заставит систему считать все
файлы новыми.

## 17. Известные ограничения

- нет автоматического старта после загрузки изображений;
- ребёнок не видит output, если ему не дан доступ к аккаунту/папке результата;
- подпапки источника не обходятся;
- максимум 1000 элементов в одном листинге текущего workflow;
- одинаковый basename у разных расширений вызывает коллизию output;
- OCR может ошибаться в именах, числах, пунктуации и на плохих изображениях;
- exhausted job требует ручного сброса attempts;
- нет автоматической проверки смысловой точности распознанного текста;
- API создан для доверенного локального контура и не имеет собственной
  авторизации; безопасность обеспечивается loopback-доступом.
